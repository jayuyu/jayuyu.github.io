Binary Ninja 架构插件怎么写

1. 架构插件

Binary Ninja 的核心思路不是“只支持固定几种 CPU”，而是把“架构”和“分析”分层：前者负责把字节翻译成指令语义，后者基于这些语义继续做 CFG、数据流、MLIL、HLIL 和反编译。所以当你面对一种自定义 ISA、虚拟机字节码，或者某个未被官方支持的处理器时，最正统的做法不是硬改现有分析结果，而是定义一个新的 Architecture。这很适合某些大厂自定义VMP的解释器架构去给他做一套对应的架构

对于逆向工程来说，这一点特别重要：

在研究VMP的时候有几种方式可以做到“反编译”其指令集，第一种就是硬解析，就跟搓一个解释器一样，

对指定的，我们已经分析好了的进行硬反编译，这样的效果当然不够灵活

还有一种就是llvmlite， 但llvmlite 只能帮你“造一个 IR 和执行/优化框架”，但不会像 Binary Ninja 自定义架构那样，天然给你接上反汇编、CFG、寄存器语义、LLIL/MLIL/HLIL 和反编译流程；做 VMP 时前者更像自建分析器，后者则是直接把虚拟 ISA 接进现成逆向平台。

2. 一个最小架构插件长什么样

官方示例和文档都表明，最小的 Python 架构插件通常包含：

  • 一个继承自 Architecture 的类；
  • 在这个类里填好架构元数据；
  • 再实现几组关键接口：反汇编文本、控制流信息、LLIL lifting。

最小骨架通常类似这样：

  • get_instruction_text 负责“怎么看”；
  • get_instruction_info 负责“怎么跳”；
  • get_instruction_low_level_il 负责“这条指令到底做了什么”。

官方 Part 1 把前两个作为第一阶段重点，Part 2 再把 lifting 和 BNIL 作为第二阶段重点。

3. 架构元数据需要填什么

给出的 Architecture 示例里，最开始就要填一批基础属性，包括：

  • name
  • endianness
  • address_size
  • default_int_size
  • instr_alignment
  • max_instr_length
  • regs
  • stack_pointer（如果有）

这些属性看起来很“模板化”，但其实非常关键。因为 Binary Ninja 后续所有地址计算、寄存器宽度推断、栈语义、以及一部分 lifting 行为，都依赖这里的定义。比如某音的那个 24 字节定长 VM 指令集（，就应该把：

instr_alignment = 24

max_instr_length = 24

明确写出来，让 BN 从一开始就按这门 ISA 的规则去切指令。这个设计和官方架构教程是一致的：先把“架构世界观”讲清楚，再写具体指令。

4. get_instruction_text：反汇编

官方 Part 1 把“能看到正确的反汇编文本”作为第一个可验证里程碑。Binary Ninja 并不要求你一开始就把 LLIL 写满；你完全可以先把字节解码成指令文本，再慢慢补后面的分析。

这个接口的职责很单纯：

给输入字节和地址，返回：

  • 一组 InstructionTextToken
  • 当前指令长度

也就是说，这一层只关心 “这条指令长什么样”。

例如可以先打印成：

add r29, r29, #-784

此时它的价值主要体现在两个方面：

  • 你终于可以用 Binary Ninja 的界面浏览虚拟机指令流，而不是只看 hexdump；
  • 你可以验证自己的解码器是否稳定。
5. get_instruction_info：CFG

如果说 get_instruction_text 解决的是“显示问题”，那 get_instruction_info 解决的就是“控制流问题”。

Binary Ninja 需要知道一条指令是不是：

  • 普通顺序执行；
  • 无条件跳转；
  • 条件跳转；
  • 调用；
  • 返回；
  • 间接跳转。

因此这个接口通常要返回一个 InstructionInfo，并填入：

  • length
  • add_branch(BranchType.TrueBranch, target)
  • add_branch(BranchType.FalseBranch, fallthrough)
  • add_branch(BranchType.UnconditionalBranch, target)
  • add_branch(BranchType.CallDestination, target)

等信息。官方教程里也是先做出 get_instruction_info，这样控制流图才会正确。

对于 VM 来说，这一步尤其重要。因为很多 VM 的 native dispatcher 是一坨间接跳转和跳表，但你真正想让 Binary Ninja 看到的，其实是“虚拟指令层面的 CFG”。这时你就需要在插件里把 VM 的分支语义直接告诉 BN，而不是把 native handler 的 br x12 原样照搬进去。

6. get_instruction_low_level_il

官方 Part 2 的重点就是这件事：

没有 LLIL，你只有“看起来像个反汇编器”；

有了 LLIL，你才真正进入 Binary Ninja 的分析流水线

因为 BNIL 的定义本身就是：

把具体架构的机器语义，翻译成架构无关的中间表示。

LLIL 处在这条链路的较低层，仍然接近汇编语言，但已经足够让 Binary Ninja 做控制流和数据流分析。官方概览文档明确指出，BNIL 是一组不同抽象层次的 IL 家族，其中 LLIL 是最接近原始指令语义、同时又能支撑更高层分析的关键层。

注：在分析VMP的handle的时候，我们盯着Low level IL其实我觉得远比直接看汇编好，因为IL我认为是比较解决硬还原VMP handle的解析地步的

LLIL 的目标不是“把原指令机械翻译成另一种语法”，而是把指令的语义动作表达出来。

举例来说，一条加法指令在 LLIL 里关心的不是原始 opcode 编码，而是：

  • 从哪个寄存器读；
  • 做了什么算术；
  • 结果写到哪里；
  • 是否影响控制流。

因此你在架构插件里写 LLIL 的时候，本质上是在告诉 Binary Ninja：

这条指令，不是长得像什么，

而是“实际干了什么”。

LLIL

Binary Ninja 官方 LLIL 文档里一个非常重要的思路是：

LLIL 是树状表达（tree-based），它不是简单的字符串拼接，也不是纯文本伪代码。你通过 il.add、il.sub、il.set_reg、il.load、il.store、il.if_expr、il.jump 这些 API，去构建一棵表达“语义动作”的树。
